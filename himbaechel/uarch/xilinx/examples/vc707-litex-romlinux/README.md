# VC707 LiteX ROM-Linux SoC (xc7vx485tffg1761-2)

The 1 GB VC707 Linux SoC (VexRiscv-SMP `linux`, 64-bit DDR3, a 128 KiB L2,
SGMII Ethernet) with its kernel, a busybox rootfs, OpenSBI and the device
tree xz-compressed into its BIOS ROM.  The ROM is 2.5 MB, so it is 640
one-bit-wide RAMB36s with contents, the most block RAM of any design in the
gate.

    cells          32360
    RAMB36E1         735   (640 of them the ROM)
    DSP48E1           12
    CARRY4           535
    MMCME2_ADV         3
    GTXE2_CHANNEL      1

Synthesised by Verilator's structural backend (jrrk2/verilator, `synthesis`
branch), not yosys; generated by xc7-bitstream-tools'
`examples/vc707-litex-romlinux/vc707_romlinux.py`.  The netlist has the
two-read block RAM fix, so the 10 LiteEth packet buffers share port A
between the write and the read at the write address (READ_FIRST).

`delay-matrix-xc7vx485t.txt` is the measured delay matrix the board builds
used, passed with `-o delay-matrix`, so the run does not depend on how the
matrix is rebuilt.

## Why this one is in the gate

It is the design that showed nextpnr's timing report could not be trusted
for deep memories.  Placed and routed before the clock-tree and block RAM
work, with these flags, it met 100 MHz on the system clock by nextpnr's
report, and on the board the ROM read wrongly: the kernel or the rootfs
failed to unpack.  The ROM test (BIOS `romtest`) found three ROM block RAMs
at the top and bottom edges of the die reading about a quarter of their bits
wrongly, with the FASM contents correct and DDR passing in full.  Two causes:

- nextpnr gave every sink of a global clock the same delay, so it saw no
  clock skew; Vivado's placement of the same netlist has -0.45 to -0.87 ns on
  those paths.
- The heap placer spread each ROM data bit's 20 block RAMs over the full
  height of the die and filled whole columns, edge columns included.

With `clock_tree.cc` and `bram_place.cc` the same netlist reads its ROM
cleanly, unpacks every image, boots Linux and takes a DHCP lease, with
nothing from Vivado.

## What the gate checks

That P&R completes and the FASM assembles, like every stretch entry, and
that the block RAM placement keeps the quality that made this design work.
`.github/scripts/bram_fom.py` scores each block RAM by its worst estimated
to the registers it feeds, from the placement alone (the delay
matrix, plus the clock-tree skew).  On the board:

| placement | ROM on the board | worst | p95 |
|---|---|---|---|
| Vivado | reads | 4908 ps | 4084 ps |
| this tree (clock tree and block RAM placement) | reads, boots | 5048 ps | 4187 ps |
| this tree, chipdb from another prjxray-db revision | reads | 5632 ps | 5083 ps |
| Vivado's block RAM sites, nextpnr logic | reads, boots | 5663 ps | 5038 ps |
| nextpnr, the netlist before the fix | reads, boots | 5995 ps | 4979 ps |
| nextpnr before this work, seed 2 | reads wrongly | 6251 ps | 5113 ps |
| nextpnr before this work | reads wrongly | 6961 ps | 5639 ps |

The worst score is what separates them: every placement that read its ROM
scored 5995 ps or less, the two that did not 6251 and 6961.  The gate fails
over 6100 ps worst, in that gap, or over 5400 ps p95, a backstop (the p95
does not separate them alone: 5083 read, 5113 did not).  The margin is about
250 ps either side, so the score flags a placement to try on the board rather
than proving one.  The log must also show the `clock-tree:` and
`bram-place:` lines, so a run where either was skipped cannot pass.

About 13 minutes of P&R on a desktop.
